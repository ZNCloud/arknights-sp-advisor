# 顾问的数学模型架构（v1 规格）

> 来源：三个旗舰模型（claude-opus-5-5 / gpt-6.1-sol / gemini-4-argon）独立设计 + gpt-6.1-sol 合成，
> 针对「现有 open-brief.mjs 的 road×gate + 专属优先」被使用者的五条实证反驳而重写。
> 本文只定架构，不含实现代码。实现严格按 §G 的文件顺序推进。

## 0. 三条被推翻的旧假设（先记账）

| 旧假设 | 为什么错 | 证据 |
|---|---|---|
| 「专属策略优先」 | `bands.json` 的 `bondIds` 只是归属标签，不代表战斗适配 | 克莱门莎（阿戈尔专属）`bond_add_type=by_charlevel` → 只给层数；而阿戈尔层数 = HP（`max_hp_per_stack=0.01`）→ 对输出的直接边为 0 |
| 「层数越高越强」用于所有盟约 | 阿戈尔层数=HP、维多利亚吃装备件数、卡西米尔吃部署次数、叙拉古吃命中次数——**同一个 220 层，战力完全不同** | 各路线 `bonds.json` 的 bb 结构不同（见 §C 表） |
| 「波次不是瓶颈」（我上一轮的说法） | `tools/balance.mjs` 的层数/装备/精锐数是**输入曲线**（coreLayers R14=150 是人写的），不是模拟出来的 → 它只能证明"给定阵容能过"，证明不了"能不能爬到那条曲线" | `tools/balance.mjs` 文件头自述把准备期效果折进人工曲线 |

另外两个此轮实测到的机制细节：

- **大帝**：`respawn_time=-0.5`，实现是「每次部署令本场再部署倍率再乘 0.5，**无上限**」（`server/sim/content/bands/battle.js`，PRTS 备注「可无限叠加」；0.2.2 前有 20 层上限）→ 对卡西米尔的突袭/远牙流是**复利引擎**，不是"方便"。
- **克莱门莎**：代码注释自相矛盾（一行写 `requireActive false`，另一行写 PRTS 要求已激活），实际 handler 调用 `gainLayers(..., requireActive: true)` → **必须先开 3 个阿戈尔才生效**，且只给 HP。两头都不支持把它当首选。

## A. 决策形式化

**同一有限时域 POMDP，两层决策：**

- 宏动作 `a₀ = (ρ, b, π)`：路线变体 ρ（含角色替代集合与转型条件）、合法策略 b、执行政策 π。
- 微动作：买/卖/刷/冻/升/选奖励/装备/布局/再部署/转型/结束准备。
- 状态 `s_t = (c, r, φ, g, gᵖᵉⁿᵈ, ℓ, u, I, J, B, L, LP, z, P, O)`：环境 `c`（模式/难度/地图/BOSS β/禁用 D/可用盟约/规则版本/胜利定义）在**开局即已知，不得在线平均掉**。
- 转移 `s_{t+1} = T(s_t, a_t, ξ_t)`，`ξ_t` 用真实引擎（Store 抽卡 + Battle + Match 结算）。
- 目标：`Q₀(ρ,b,π|c) = P(Y=1 | c,ρ,b,π)`，Y 由 `victoryDefinition` 明确（普通 BOSS / 隐藏 BOSS 分开报）。

**不求解完整 POMDP**：每路线准备少数可复现政策模板，训练种子内选政策、冻结后留出种子评估；开局从政策族选宏动作，回合内建议做有限前瞻 `ΔQ(a) = Q(μ_t,a) − Q(μ_t,a_baseline)`。两层共用同一套 T/K/战斗引擎/成型定义。

## B. 胜率 / 成型率 / 高 roll 率（三个量、三个分母）

| 量 | 定义 | 说明 |
|---|---|---|
| 通关率 `p_win` | `P(Y=1)`，所有轨迹为分母（提前死亡算 0，不剔除） | 默认排序主键 |
| 成型率 `p_form` | `P(F_r)`，`F_r = {此前存活 且 关键回合快照 Z_r ∈ 可赢区域 𝓦_c,r}` | 回答"能不能滚起来" |
| 高 roll 率 `p_hr` | `P(H_r)`，`H_r = F_r ∩ {U > x_hr,c}` | 回答"胡不胡" |

分解（是解释，不是近似）：`p_win = P(F_r)·P(Y|F_r) + P(¬F_r)·P(Y|¬F_r)`。

**可赢区域**：固定快照时点 = **关键回合准备结束、战斗开始前**（不能用 R12 打完后的层数解释 R12 是否过关）。在快照上做干预扫描层数 L，重跑真实后续模拟，拟合 `V_r(Z,c) = P(Y|Z,π⁺)`，取 `𝓦 = {V ≥ q_safe}`（q_safe 先配 0.90，这是**决策安全线，不是游戏参数**）。层数阈值 `X = inf{L : V ≥ q_safe | 其余状态固定}`；不存在则 `X = null` 并记「仅加层不足以成型」——**阿戈尔通常就是 null**。

**高 roll** 用具可复验的「终局速杀余量」：`U = −E[min(T_kill, t_cap)/t_cap]`，参照分布 `𝒟_ref,c` 由预先公布的已验证路线/策略集合等权构成并冻结，`x_hr,c = Q₀.₈(U; 𝒟_ref,c)`。比较策略时不得各自重算分位；样本不足就报「阈值未校准」，不塞一个任意倍数。

## C. 路线「资源 → 输出」转换

每条路线的转换函数必须保留（不许只留一个标量）：

| 路线 | 必须保留的转换 | 吃的是什么资源 |
|---|---|---|
| 炎 | 攻击 +0.23+0.009L；6/9 人档解锁炎佑，属性继承真实炎成员属性和 | L、有效人数、召唤物存活 |
| 谢拉格 | 条件替换（非相乘）：普通 ×1.25；对寒冷/冻结 **替换为** ×(1.35+0.01L) | L、控制覆盖、BOSS 抗控 |
| 拉特兰 | 弹药 floor(ammo₀×(1.05+0.015L))；6 人档耗弹叠攻有上限 | L、弹药技能身份、耗弹率、技能空窗 |
| 卡西米尔 | 攻击 +min(0.2·N_deploy(t), min(0.50+0.01L, 2.0))；6 人档阻挡真伤脉冲 | **部署事件时序**、L 抬上限、再部署配件 |
| 维多利亚 | 带装备者 ×(1.25+0.008L)；6 人档每件装备加攻（普通 `atk_normal_equip` + 精锐 `atk_golden_equip`）；每 25 层发装备 | **有效装备件数与阶**、6 人档 |
| 叙拉古 | 部署窗口攻速 25+0.8L；隐匿命中 3% 概率真伤 5000+50L | L、窗口覆盖、**合格命中次数**（3% 是 PRD 长期率，有限战斗不能当独立伯努利） |
| 阿戈尔 | 生命 ×(1.35+0.01L)；吞噬按实际顺序获得基础攻击最终加算与阻挡；5 人档复活额度 | **吞噬目标身份/位置**、外援、装备；L **没有直接 ATK 边** |
| 萨尔贡 | 技能启动叠临时 K≤25 每栈 +12 攻速；持久 L 决定栈持续时间 | 技能启动率、K 占空比、装备共享布局 |

**两类量要分开存，不能混**：伤害弹性 `ε_x = ∂log D/∂log x` 与胜率影子价格 `λ_x = Δp_win/Δx`。不能把 ε 当 λ（尤其不能给阿戈尔生命层随手指定一个胜率权重）。

**自动化的入口**是 `effect_semantics.json`：把 `(外层 key, bbStr 内层 key, 参数谓词, 引用对象)` 映射到 `(事件, 目标, 操作, 公式, 上限, 重置, 结算位置)`。语义**人工审一次**，随后 23 盟约 + 40 策略的参数提取与机制图自动生成；未支持的键标 `unsupported`，**受影响候选禁止报精确胜率，而不是记 0**。

## D. 40 条策略的事件向量化

不是 40 个固定常数向量，而是**事件核** `K_b` + 条件产出：

```
v_{b,r}(s,a) = E[ΔR_b | s,a]        Σ_{b,r}(s,a) = Cov(ΔR_b | s,a)
```

维度必须带单位：即时/待发金、节省费用、干员份数（按身份/阶）、不同成员、调和、精锐、装备（按身份/质量/分配）、各盟约层数 L、攻击加算、攻速、生命、SP、再部署倍率、复活额度、控制、防空、奖励机会、额外敌人风险。

必须区分的语义：**「商店出现」≠「免费获得」≠「增加不同成员」≠「完成精锐」≠「占场位后的有效人数」**；凯瑟琳的「3 选 1」是一次选择机会，效用是 `E[max_j u_ρ(item_j, s)]`，不是 3 件入库。

**适配（路线×策略）不是点积终判**，而是因果配对差：

```
A(ρ,b|c) = p_win(ρ,b,π_{ρ,b}) − p_win(ρ,b₀,π_{ρ,b₀})
```

b₀ 必须是合法基准策略（反事实无策略只用于机制消融）。点积/影子价格只用来**分配模拟预算与生成解释**，不能永久剪掉候选。

40 条逐条编译要求见合成原文 D2 表（每条都写明通道、条件、易错点），例如：鸭爵=R5 起替换敌人、击倒者得 1 金（要计归属与可花时点）；老鲤是**收入替换**不是 +15；潘格尼尼是累计 55 金**送一次**；余是 R8 单盟约 36 层 / 多盟约各 12 层；哈洛德 R4 起每 2 回合赠**干员**。

## E. 概率模型与校准

**能解析算的**：模式/禁用过滤；单次刷新命中 `P(hit G) = 1 − (1 − Σ_{i∈G} p_i)^S`，其中 `p_i = max(0,n_i)·1{i∈E_ℓ} / Σ_j max(0,n_j)`；固定库存下的首次命中；已知收入下升级路径可行性；给定候选分布的选择收益。

**必须模拟的**：资金清空/保留、升级降价、奖励选择、追精锐、装备分配、多人占池、战斗层数、死亡/再部署、击杀资金、机变与转型的联合尾部。

**不能套的简化**（原文明确否决）：集齐不同成员不能用"人数 m"的 DP（要身份子集）；追三份在有库存反馈时必须更新核；泊松化 coupon collector 只能作近似并验证；特殊刷新/冻结/复制/装备候选不能套独立槽公式。

**禁用规则的两个坑**：8 核心取 3、15 附加取 4 的组合数 76,440，但各模式集合与数量不同；复刻的干员移除条件是**该干员所有所属盟约都被禁**，不是任一副盟约被禁就删牌。

**校准**：完整联合轨迹只能用事件驱动蒙特卡洛；多人未知池 v1 只给低/中/高竞争情景并报范围（无数据权重时不擅自等权）。每次比较用相同 `c` 与可比外生随机流（商店/奖励/敌人/战斗/队友/政策各自命名子流，配对种子）。

## G. v1 最小可实施范围

**收窄验证域**：单人 + 一个明确长局模式 + 三条争议路线：

- **阿戈尔**：克莱门莎 / 卡莱莎 / Pith + 合法基准策略
- **维多利亚**：哈洛德 / 凯瑟琳 / 鸭爵 + 合法基准策略
- **卡西米尔**：大帝 / 玛恩纳 + 合法基准策略

40 条仍全部做语义登记，**未验证路线不参加精确概率排名**；对外只说"已评估候选中最佳"，不称全局最优。

**v1 只估五组量**：① 关键回合前存活概率；② 关键角色/有效人数完成概率与首达回合；③ 指定回合升级与投资可达性、资金缺口；④ 有效装备分配 / L、K / 部署-死亡循环的联合状态分布（P10/P50/P90）；⑤ 完整真实通关率与快照后续可赢区域 → 由此导出成型率、高 roll 率。

**文件顺序（严格按此推进，统一放 `advisor-dev/model/`，不改仓库的 `data/*.json`）**：

1. `model_manifest.json` — 冻结规则/时钟/胜利定义/策略数量/证据等级/未支持项（先解决克莱门莎激活条件的规则差异）
2. `effect_semantics.json` — 先审 8 条争议策略，再覆盖 23 盟约 + 40 策略
3. `hypotheses_and_experiments.json` — 事前固定对照组、扫描参数、种子组、误差目标、拒绝条件
4. `compiled_band_effects.json` + `route_mechanisms.json`
5. `policy_templates.json` — 三条路线的可复现政策（含经济策略的节奏变体）
6. `scenario_state.json` + `trajectory_samples.jsonl` 契约 → 真实 Match 驱动 + 快照战斗适配入口
7. 先做语义/池单元实验，再采轨迹（每候选 200 条筛查）
8. `combat_calibration.json` — 真实快照后续回放估 V、多维成型边界、可用 X、固定高 roll 参照
9. `candidate_estimates.json` — 冻结候选/政策后 ≥400 条独立留出轨迹
10. 最后实现 `opening_advice.json` 响应，替换 `open-brief.mjs` 的 road×gate 与专属优先；插件与 overlay 接同一响应

**上线门槛**：效果语义全覆盖 + 轨迹可重放 + 关键概率留出校准达预定误差 + top 候选差值未分辨时显示并列 + 规则/政策版本变化即失效缓存。

## 我的判读（写给使用者）

这套架构的代价是真实的：**它把"拍脑袋的评分"换成了"可校准的估计"**，v1 就要真实跑几百条完整对局轨迹。但它带来一个之前没有的东西——**每个结论都能被数据推翻**（§F）。你指出的三条错误之所以能进去，是因为旧模型没有任何一条假设写明了"什么数据能推翻它"。

如果嫌重，最小可用的降级是：先做 1–2（manifest + effect_semantics）+ 4（compiled_band_effects），把 40 条策略编译成带单位的事件向量，然后**只做你问的那三组对照**（阿戈尔：克莱门莎 vs 卡莱莎 vs Pith；维多利亚：哈洛德 vs 凯瑟琳 vs 鸭爵；卡西米尔：玛恩纳 vs 大帝），用 `tools/balance.mjs` 的引擎跑真实战斗——这三组对照的结果本身就已经能回答"什么情况下更好胡"。
